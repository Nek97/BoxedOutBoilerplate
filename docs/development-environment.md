# Setting up the Development Environment

You can setup your dev environment in 2 ways:

- **Docker (Suggested)**: by using docker-compose and the integration with VSCode Dev Container. This is the preferred way because you won't have any dependency discrepancy and all developers will work on the same dockerized environment.
- **Host**: By installing completely (or partially) the dependencies on your host. This is not suggested because if you have a different version npm/node or anything else needed by the app to work, you could encounter unwanted behaviours.

## Docker Setup: develop within the container

### Container folder permissions on binded volumes

The Dockerfile generated by the pipeline configures a non-root user for the container. This user has the `uid=1000` and `gid=1000`.

**NOTE:** If you are on Linux, in order to create files with the proper permissions when you use the container you need to make sure that you have an user with those IDs in your system and that this user has read/write permissions on the current folder. Alternatively, you can re-build the docker image setting the USER_ID and the GROUP_ID
within your `docker-compose.override.yml` file, uncomment and use the **build** configuration instead of pulling the image.

If you want to use Git within the container shell, you have to share the git credentials between the host and the container.
The easiest way to do it is via setting up a Git Credentials Helper and cloning the repository using https, if you do so the credentials will be automatically passed through Docker. [Readme](https://docs.github.com/en/free-pro-team@latest/github/using-git/caching-your-github-credentials-in-git)

**NOTE:** If you are using the WSL on Windows, you can set the Credentials Helper using the following path:
`git config --global credential.helper "/mnt/c/Program\ Files/Git/mingw64/libexec/git-core/git-credential-manager.exe"`

More info about how to [work within the container here](https://code.visualstudio.com/docs/remote/containers).

### Git inside of the container

Since it is undesirable to restart your container every time you want to check out a different branch or want to pull updates, we tried to make it possible to work from within the container.
All git operations should function as well from within the container. Although for windows users it might be required that you have originally pulled the repo through HTTP instead of SSH.
Please try out in the terminal in your container, if your git configuration still functions, if not try to clone the repo through HTTP and retry. If this still does not work, contact our admin for support on setting your agent.

### Tip about the npm modules

The pulled dev image comes with a pre-built **npm_modules** folder which potentially contains all the needed modules. However, if you are switching to a branch that adds
new modules or if you are pulling updates by using git, you may still need to run a `npm run install:workspaces` to get the new modules.

## Host Setup: Setup the environment locally

Alternatively to the **Docker setup** you can install all the dependencies locally, although it's not the suggested way to develop with the BCA project for the reasons explained above.
**NOTE:** It's **very important** to stick with the version of the requirements listed within the README to avoid issues as much as possible.

### Installation

1. Create an `.env` file in your repo root folder and add `NODE_ENV=development`. It will make sure that the application will load the `conf/dist/.env.development` and `conf/dist/.env.local.development` configurations that should work with the default mysql setup on docker
2. Run the server dependencies by using `docker compose up -d mysql mysql-test redis` if you do not want to them in your host. If you prefer to point your application to a different mysql server, you can add the `MYSQL_HOST=` and `MYSQL_PORT=` environment variables to the `.env` file and configure all the `MYSQL_*` variables accordingly to your MySQL setup.
3. Run `npm run install:workspaces`

**NOTE**: If you're not our mysql container and you want to run the e2e on another server, you have the possibility to create and configure 2 env file: `.env.development` and `.env.test` and run the e2e with the `NODE_ENV=test` environment variable set in your command to switch between them

## Set the default project

The BoxedOut Core API uses the [NestJS monorepo](https://docs.nestjs.com/cli/monorepo) to allow us developing multiple applications within the same repo. It means that you would have to manually specify which project to run/build/test when you run such commands. To simplify this process we have created a npm script to set a default project using the [npm config](https://docs.npmjs.com/cli/v7/commands/npm-config).

`npm run set:proj <project-name>` where `<project-name>` can be: `manage-panel`, `cli`, `gateway` etc.

If you want to work on all projects at the same time, you can set `all` as **<project-name>**. It will allow you to start/build/test all projects at once.

NOTE: You can find the list of the projects within the nest-cli.json file

## Running the app

Once you're inside the devcontainer, you have to run the application by your own using one of the following command:

```bash
# development: transpile the code and serve the application
$ npm run start

# watch mode: transpile, serve and hot-reload the code upon changes
$ npm run start:dev

# production mode: serve the pre-build (npm build) application
$ npm run start:prod

# command to start all services at once
$ npm run start:all

# command to start all services at once with hot-reload enabled
$ npm run start:all:dev
```

## Test

```bash
# unit tests
$ npm run test

# e2e tests
$ npm run test:e2e

# run test coverage check
$ npm run test:cov

# run all checks, including linter
$ npm run check:all
```

**NOTE:** both `test:cov` and `test` can be followed by the path of a specific spec file to test. This is particulary
useful when you have to quickly test a specific file instead of the entire project.

## Env files

The boxed-out-boilerplate uses the NestJS ConfigModule to load different .env files at the startup to default- or user- defined configurations for different installation types and environments.

The env files are loaded in the following order of priority:

- **.env** - user-defined, git-ignored
- **.env.{environment}** - based on NODE_ENV, user-defined, git-ignored
- **/conf/dist/.env.shared** - always loaded except in production
- **/conf/dist/.env.docker.{environment}** - based on NODE_ENV, only loaded when the app run under our `docker compose`
- **/conf/dist/.env.local.{environment}** - based on NODE_ENV, only loaded when the app is not executed under our `docker compose`

**NOTE:** the variables are not overwritten by the files with a lower priority.
